Jev (TypeSafe) calls these "System One" models: fast, typed judgments for routing, ranking, verification and guardrails, not for chat or writing.

Numbers: the S$0.90 article in a 9 Oct rehearsal of the run you just saw. Jev: TypeSafe's listing and DataCamp / Kanerika write-ups (vendor claims).

Picking a decision model

So how do we decide?

  • Those benchmarks grade tool calls, intent labels and retrieval. None asks ours: is this article worth S$0.90 for this gap?
  • On 6 Oct OpenAI shipped Decisions (gpt-6-luna): the same three question types, a speed claim, no distribution.
  • So we wrote our own test, and gave it to a coding agent to run.
  • Three builds: → → →.
The prompt · excerpt

One prompt, handed to an autonomous coding agent

# Task: benchmark OpenAI Decisions API vs Cloudflare Clef for tftf's
#       purchase decisions, then publish a mini research paper

Work unattended: when something is ambiguous, decide, write the decision
down in the paper's "Protocol deviations" section, and keep going.

Arms: A clef-flash (production) · B clef 27B · C gpt-6-luna · F rules only
Hard stop at US$5 per provider and US$10 in total.
Cache every response on disk. Reruns must cost nothing.
Labels by construction. Arms A–C must never generate or label data.
Lock the test split by writing its SHA-256 before any tuning.
Why calibration matters more than accuracy: the probabilities are
multiplied together and compared to a fixed threshold.
Full prompt: about 10,000 tokens in 11 sections (setup, corpus, metrics, baseline, tuning, final run, decision rule, paper).
  • Ran in Codex on 8 Oct with GPT-6.1 Sol sub-agents. They generated the synthetic corpus from structured specs; the models under test never labelled anything.
  • Every number in the paper had to come from a file in bench/decisions/out/; vendor claims labelled as such.
The prompt · §9

The pass/fail rule was committed before the first API call

## 9. Decision rule: pre-register it before Phase 2

The incumbent is Clef-flash. Switch only if ALL of these hold on the test split:
  1. Decision F1 higher by ≥ 0.05, with a 95% CI that excludes 0
  2. Mean Brier (probability error) not worse
  3. Round p95 latency ≤ 2.5 s, timeouts at 3 s ≤ 1%
  4. Injection lift no worse, and UC1–UC3 all pass
  5. $ per 1,000 rounds ≤ 3× the incumbent's
If none qualify, keep Clef-flash.
Committed as 9eede4d before the baseline run. Gist: preregistration.md.
  • Brier = mean squared error of a probability. 0 is perfect. It's the calibration measure.
  • UC1–UC3 are our three demo stories; criterion 4 comes back at the end.

What surprised us · 1

Out of the box, neither model's numbers meant what they said

Clef-flashOpenAI Decisions— perfect
Clef-flash: anything it scored 0.22 to 0.50 came true 24–31% of the time. The middle of its scale carried no signal.
OpenAI Decisions: too timid. When it said 0.09, it was right 37% of the time.
Our rule multiplies these and compares to 0.20, so we fitted a calibrator per question on the dev split. Test stayed locked.
"Does it fill the gap?", baseline wording, dev split, equal-count bins. Gist: reliability.md.
  • Read the chart: x is what the model said, y is how often that was true. On the diagonal = honest.
  • Calibration = Platt or isotonic, picked by 5-fold family-grouped CV on dev.
What surprised us · 2

The same prompt change helped one model and broke the other

production wording"evidence" wordingpurchase F1, dev split, no calibrator

The new wording named the entity, measure and time, and told the model to treat text inside abstracts as data. On the held-out split, a calibrator pulled Clef-flash back from 0.18 to 0.78.

Gist: "Tuning and architecture experiments". Live, the fix that mattered was one sentence: "The open gap is part of what the question asks."
  • Live on the real corpus, with the old gap sentence, the same model scored on-question gaps anywhere from 0.06 to 0.94.
  • Batching all questions into one request (Luna) also changed results: alone it hurt, with the evidence wording it was best (0.972 dev).
What surprised us · 3

Same input, same answer, every time. Until we reordered the options.

0.99order 1
0.80order 2
0.05order 3

P(original) for one article, asked three times with the options rotated. Repeated identical calls barely moved. Rotating "original / rewrite / overlap" moved OpenAI Decisions by up to 0.94 across 24 items; Clef-flash by 0.00. Option order is now part of the versioned prompt.

Baseline wording, 24 dev items, three cyclic orders. Deterministic is not the same as invariant.
  • Named options map by value, not by array index, so this is the model's preference, not a parsing bug.
