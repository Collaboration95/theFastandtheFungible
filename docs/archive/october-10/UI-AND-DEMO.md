# October 10: UI and demonstration implementation plan

Planning baseline: October 2, 2026; demo: October 10. [INTERFACES.md](INTERFACES.md) overrides older UX behavior. Keep React/Express/TypeScript, Overview/Sources/Activity, guided setup, disclosures, and the drawer. Demonstrate a material gap, one selectively approved purchase, evidence-bound impact, and a justified stop. A no-purchase answer is also successful.

## Consumption boundary and delivery order

Consume the shared proposed **run, decision, quote, purchase, and impact projections** through their owning module's exported TypeScript contracts. The following field descriptions are integration requirements, not another wire schema or persistence model. RES-02 owns run status/revision and allowed research commands; RES-03 owns baseline/updated answers and impact; COM-03/04 own exact approval, intent identity, settlement, delivery, grants, and recovery commands. COM-01 owns their durable storage relationship. UI stores only unsent setup edits and the active run pointer locally; selections, tabs, and dialogs are transient.

Dependency-safe slices: October 2–3, build presentation/tests against agreed projections; by October 4, wire the first complete flow; October 5–7, complete variants/recovery/readability; October 8–9, freeze and rehearse. Controlled responses prove rendering only; completion requires integrated API/publisher evidence. Agree contracts before replacing handlers; unavailable actions stay disabled with explanations. No alternative client state machine.

## UI-01 — Authoritative run, proposal, exact approval, and recovery

**Priority: P0. Outcome / 80–20 reason:** Show agent progress, why one source helps, exact approval, and safe recovery. Replace misleading state inference within existing surfaces.

**Current-code anchors:** `src/App.tsx`: `ServerState`, `approvePlan`, `act`, `confirmPurchase`, `recoverPurchase`, `ActivityRail`, `AgentActionStep`, `PurchaseConfirmation`, and SSE effects. `approvePlan` currently posts five `/step` transitions; recovery only inspects a source-keyed receipt and clears the modal. Confirmation generates a new random key each submission and parses error wording. `SourceItem` decides skip/block by source ID. `src/ui/index.tsx`: `ApprovalModal`, `EvidenceDrawer`, `ProgressPanel`. Existing verification: `tests/uo-07-10.spec.ts` covers cancellation, focus, pause/resume/stop/reload; `tests/e2e.spec.ts` covers protected evidence and optional purchases.

**Dependencies:** RES-02 run/decision projections and transition commands; COM-01 storage seam; COM-03 exact quote/approval/intents; COM-04 purchase-status, reconciliation, retry-delivery, and verified access. Presentation can start against agreed sample payloads; recovery and approval integration cannot finish before COM commands exist.

**Ordered subtasks**

- [ ] UI-01.a Import owner types at the API boundary and remove duplicated permissive UI types as their replacements land. Map run status, revision, stop reason, gap, decision rationale, and allowed commands to existing cards. Render discovering/reading/evaluating, awaiting approval, paused, complete, abstained/limited, and recoverable failure without inventing percentages or marking Search complete early.
- [ ] UI-01.b Replace the five-step loop with RES-02's start/continue orchestration contract. Show committed progress after each checkpoint. SSE invalidates/refetches snapshots and may display an explicitly unvalidated synthesis draft; reload/reconnect always fetches authoritative state. Ignore wrong-run or older responses, cancel obsolete requests on navigation, and serialize local command submission. Missing events must not stall a completed snapshot.
- [ ] UI-01.c Put the current proposal beside the baseline/gap in Overview: targeted question, expected marginal evidence, quoted cost, duplicate/independence rationale, and remaining authority. Source actions consume server eligibility/reasons rather than named-source heuristics. Keep inspection available when buying is blocked. Decline/skip uses the owner action and leaves an open-evidence answer available when supported.
- [ ] UI-01.d Review the immutable COM quote in the existing approval dialog: publisher/payee, resource/version, amount and unit/currency, settlement mode, expiry, terms, quote identity, and run/intent binding. Display settled and reserved spend plus server-projected available authority. Preserve all binding fields; long identifiers can live in a disclosure. Confirm submits the exact server-issued binding once; plan approval, budget entry, opening the dialog, and Enter outside Confirm never purchase.
- [ ] UI-01.e Replace string-matched failures with typed purchase status and safe actions. Show expired/changed quote, mandate block, unresolved settlement, paid-but-undelivered, digest/version rejection, and verified grant distinctly. Refresh quote requires renewed review/consent; reconcile targets the same intent; retry delivery targets the existing paid receipt and cannot charge again. COM decides whether a same-intent execution retry is safe. Network timeout means unconfirmed outcome, never “nothing purchased.” Refetch after every recovery command.
- [ ] UI-01.f Keep one active dialog: close/suspend the evidence drawer before approval. Maintain focus containment and restoration through busy-state changes, Escape/backdrop cancellation before submission, inert background interaction, and a usable close/status path after submission. Closing a pending dialog dismisses presentation only. Announce material status changes once, not every SSE token. Map safe error copy while retaining diagnostic identifiers outside the primary message.

**Technical decisions / failures:** A BUY decision is not proof of readable content; render unlocked only from COM's verified version grant. Quote expiry can disable Confirm locally for clarity, but the server validates expiry and revision. A rejected stale command refreshes state and requires review; never silently replace an approved quote. Reservation accounting and intent identity are server-owned, including across reloads and double clicks. If snapshot retrieval fails, label the last view stale and disable mutations while preserving inspectable already-accessible evidence. Stop/pause act through RES-02 and must not claim to cancel an already submitted payment; COM status remains visible for outstanding delivery/reconciliation.

**Observable acceptance:**

- Plan approval starts meaningful research progress without five browser-driven stages; a waiting run cannot spend until exact confirmation. Finish/abstain shows its stop reason and no purchase CTA unless the server permits one.
- Cancel review, decline, duplicate click, stale revision, changed price/version/terms, expired quote, and reconnect never create an extra authorization or charge. Unknown outcomes remain unresolved after modal dismissal and reload.
- Reconcile and delivery retry produce observable COM requests for the same intent/receipt; delivery failure remains locked, successful retry exposes only the verified version, and settled/reserved totals do not change on delivery retry.
- Keyboard-only approval works, focus cannot reach background controls, cancellation restores its trigger, and pending/blocked/failed states have text explanations beyond color.

**Verification / required evidence:** Extend existing `tests/uo-07-10.spec.ts` and `tests/e2e.spec.ts` for request bindings, reconnect ordering, decline, repeated confirmation, quote refresh, timeout reconciliation, and paid delivery retry. Coordinate COM fault injection with the small VER scenario runner; capture run/intent/quote/receipt IDs and ledger-before/after assertions from the integrated route tests. Extend existing `tests/a11y.spec.ts` to scan proposal, approval, and recovery states with zero serious/critical axe violations. Proposed additions are test cases, not existing coverage or scripts. Existing commands: `npx playwright test tests/uo-07-10.spec.ts tests/e2e.spec.ts tests/a11y.spec.ts`, plus `npm run typecheck`.

**In / out / done:** In: authoritative presentation, approval/recovery wiring, accessibility. Out: settlement, storage, transition engine, generic controls, new libraries, redesign. Done when acceptance passes against owner APIs and screenshots/traces, exit statuses, and eventual implementation commit are recorded.

## UI-02 — Before/after evidence impact and exact passage navigation

**Priority: P0. Outcome / 80–20 reason:** Trace material impact—or an unchanged conclusion—to the acquired passage. Two answer states and one exact citation prove value without analytics.

**Current-code anchors:** `src/App.tsx`: `WorkingAnswer` creates fallback thesis claims from the first two readable sources; `citationTargets` pairs parallel source/span arrays by position; `answerReadiness` checks existence without exact source ownership; `DossierPanel` renders `changedAfterPaidResearch` with Northstar/Grid labels; `sourceQuote`, `QuoteStrip`, `openSource`, and `EvidenceDrawerPanel` lack version-bound navigation. `src/domain.ts`: `Claim`, `DossierDraft`, and unversioned `evidenceSpans`. Existing `tests/e2e.spec.ts` checks an open citation and locked premium text; `tests/a11y.spec.ts` currently scans only the ready desk.

**Dependencies:** RES-01 explicit source/resource/version/family/span identities; RES-03 frozen baseline, updated synthesis, validated claim references, impact classifications and limitations; COM-04 grant visibility. UI-01 provides snapshot ordering, authoritative access, and dialog behavior. Render samples independently, then integrate RES-03; do not derive an impact object in the browser.

**Ordered subtasks**

- [ ] UI-02.a Consume RES-03's baseline captured before purchase and updated validated answer after delivery, each bound to its checkpoint/evidence set. Replace hardcoded publisher sequences with a compact Before / After panel in the existing answer area. Render server classification—strengthened, qualified, contradicted, unchanged—and a short explanation with material claim references. Preserve the baseline on reload.
- [ ] UI-02.b Present acquired source/version, exact cost/receipt status, which gap it addressed, supporting/challenging passage references, and remaining uncertainty. Distinguish expected benefit before purchase from observed impact afterward. A paid delivery still pending says “impact unavailable”; payment success alone never means the gap was resolved.
- [ ] UI-02.c Use owner-provided citation tuples for source, resource/version, and span rather than positional arrays or fabricated fallback citations. Before opening, fetch run-scoped authorized detail for that tuple. Select/highlight and scroll to precisely the passage, show source/family/version attribution, and restore focus on close. Guard rapid citation changes so late fetches cannot open the previous source.
- [ ] UI-02.d Render no-purchase completion, missing/empty baseline, insufficient evidence, contradictory evidence, unchanged conclusion, and invalid/unavailable citation explicitly. Remove preview-as-quote and guessed-first-source fallbacks. An absent validated claim remains a limitation; an unvalidated streamed draft remains separate from the finished answer and is not citation-authoritative.
- [ ] UI-02.e Adjust existing `src/styles.css` tokens/selectors for the payoff, primary quote, price, and mode text: target at least 18px answer/passage text and 16px primary action/status text at 1280×720. Keep detailed hashes subordinate, wrapping and inspectable. Verify contrast, 200% zoom, reduced motion, and narrow reflow without horizontal overflow; do not add a presentation dashboard.

**Technical decisions / failures:** The owner determines whether impact is semantically supported; UI neither computes confidence uplift nor treats a new citation as proof of changed belief. Before and after may be identical and must remain so. Contradiction uses explicit challenging/uncertain language instead of a success badge. Accessible open spans require no payment; protected previews cannot appear in claim quotations, hidden elements, print, or accessible names. For missing, wrong-source, or wrong-version references, show “Passage unavailable” with a safe return; never substitute another passage or trigger a purchase implicitly.

**Observable acceptance:** One purchase displays a persisted baseline and updated conclusion with its truthful impact class; the payoff citation opens exactly one matching version/span. Reordered source lists and spans do not alter its target. Unchanged and contradicted fixtures retain their classification and uncertainty. Empty/premium-only/invalid-citation states cannot claim a citable answer; no-purchase answers show no purchased-impact claim. A paid-but-undelivered source supplies neither quotations nor after-answer impact. Projector screenshots make the conclusion, passage, status, and spend readable without opening developer tools.

**Verification / required evidence:** Extend existing `tests/e2e.spec.ts` with strengthened/qualified/contradicted/unchanged and missing/wrong-version cases, plus before/after reload and rapid citation selection. Fixture responses prove UI handling; integrated RES-03/COM-04 scenarios must prove access and exact joins. Add later-state axe scans to existing `tests/a11y.spec.ts` for final answer, contradiction, empty state, and passage dialog. Preserve `tests/uo-07-10.spec.ts` keyboard/zoom/reflow checks. Record reference tuples, impact projection excerpts, grant state, browser traces, 1280×720 screenshots and 200% zoom evidence. Existing focused command: `npx playwright test tests/e2e.spec.ts tests/a11y.spec.ts tests/uo-07-10.spec.ts`.

**In / out / done:** In: impact presentation, exact navigation, limited states, readability. Out: synthesis/evaluation, alternate persistence, evidence graphs, numerical value claims, new domains. Done when output/citation failures pass, manufactured citations are removed, and artifacts/results plus eventual implementation commit are recorded.

2. Review may create a nonexecuting DRAFT. Reset atomically returns a fresh unapproved DRAFT; adopt it and show review. Reserved/submitted/unknown commerce blocks reset. These planned changes supersede the older UX wording.
3. Use the exact three-profile seed mapping in INTERFACES and replace parallel citation arrays with owner tuples. Family provenance remains independent of profile authorization.
4. Update legacy fixture tests/documentation that prescribe two purchases, XRP/SGD conversion, or live-equals-Testnet. Keep useful protected-access and keyboard assertions while aligning the stage path to one purchase and unit-explicit simulated settlement.
